Do the backends agree?

Every backend starts from the same bytes and runs the same sequence of operations. This measures how far they drift apart.

Why exact agreement is the wrong bar

Floating-point addition is not associative, and a GPU sums a reduction in a different order than a CPU does. The two answers differ in the last bits and always will.

What matters is whether the gap stays at rounding level — around 10⁻¹⁵ relative in float64 — or grows into different physics. Run this in float64; in float32 the rounding floor is near 10⁻⁷ and a tight tolerance is meaningless.

This flow is not the benchmark

What you are looking at is a separate WebGL implementation of the same D2Q9 scheme, running on your GPU to fill the background at 60 fps. The timed kernel is the Python solver in fluidbench/lbm.py, and only the numbers on the other tabs come from it. Comparing the two would be exactly the mistake this project exists to argue against.

It also drives the flow with an inlet strip, which the Python solver has not got: that one is fully periodic and unforced, so its mean velocity decays as the cylinder takes momentum out. Fine for a few thousand timed steps, wrong for a background that runs all afternoon. Turn the inlet off below to watch it decay the way the real one does.

Flow controls

What makes these numbers trustworthy

        
    
          
  • Warm-up. The first GPU steps pay for context creation, kernel
            loading and allocator growth, and the clocks have not ramped yet. Warm-up steps
            run untimed.
    • 
          
  • Synchronize before stopping the clock. CUDA calls are
            asynchronous, so a naive timer measures how fast Python can queue work,
            not how fast the GPU finishes it. Skipping this is how benchmarks "prove"
            1000× speedups.
    • 
          
  • Identical starting data. The initial condition is generated
            once on the host from a seeded generator and copied to each device, so no
            backend gets an easier problem.
    • 
          
  • One run at a time. This server refuses to start a second run
            while one is in flight — two benchmarks sharing a device measure neither.
    • 
        

        
The GB/s column comes from a minimum-traffic model: streaming must
          read and write all nine populations per cell per step. Real traffic is higher,
          because the solver materialises temporaries instead of fusing the step. Treat it
          as a lower bound.
